# SophyGo — техническое задание для AI-разработчика

**Версия:** 1.0  
**Дата:** 19 ноября 2026  
**Статус:** Начало разработки  
**Основной принцип:** Browser First — сначала браузерное приложение, затем Telegram Mini App и MAX Mini App.

---

# 1. Описание проекта

SophyGo — интерактивный туристический путеводитель с AI-Гидом.

Пользователь открывает приложение, видит карту своего местоположения и расположенные поблизости достопримечательности. При приближении к интересному объекту Гид предлагает рассказать о нём.

Пользователь может:
- Посмотреть достопримечательность на карте.
- Открыть карточку объекта.
- Посмотреть фотографии.
- Послушать рассказ Гида.
- Задать Гиду вопрос текстом или голосом.
- Получить ответ с учётом текущей достопримечательности и контекста путешествия.

SophyGo должен работать как самостоятельное веб-приложение и впоследствии запускаться внутри Telegram и MAX.

# 2. Главная задача текущего этапа

На первом этапе необходимо создать работающее браузерное приложение.

Приложение должно запускаться локально на компьютере разработчика и открываться по адресу:

`http://localhost:5173`

При этом интерфейс изначально должен проектироваться с учётом мобильных устройств.

**Важно:** браузерная версия — не отдельный продукт и не временный прототип, который впоследствии придётся переписывать. Это основа будущего приложения SophyGo.

# 3. Технологический стек

## Frontend

- React
- TypeScript
- Vite
- Leaflet — интерактивная карта.
- OpenStreetMap — картографические данные.
- CSS Modules или обычный CSS.
- Browser Geolocation API — определение местоположения.

Не добавлять UI-фреймворки и дополнительные библиотеки без необходимости.

## Backend (последующий этап)

- Go
- Chi — HTTP Router.
- PostgreSQL.
- PostGIS.
- pgx — работа с PostgreSQL.

## Инфраструктура (последующий этап)

- Docker Compose.
- PostgreSQL.
- Go API.

На первом этапе backend не обязателен. Допускается использование тестовых данных на frontend.

# 4. Архитектурные принципы

1. Не создавать отдельные приложения для браузера, Telegram и MAX.
2. Весь основной интерфейс должен быть платформонезависимым.
3. Интеграцию с платформами изолировать через Platform Adapter.
4. Не смешивать логику карты, геолокации и AI-Гида.
5. Не усложнять архитектуру ради гипотетических будущих требований.
6. Предпочитать простые решения, которые можно поддерживать одному разработчику.
7. Не создавать микросервисы.
8. Не добавлять Redis, Kafka и Kubernetes.
9. Не внедрять глобальное состояние приложения без реальной необходимости.
10. Не добавлять зависимости, если задачу можно решить штатными средствами React и браузера.

# 6. Пользовательский интерфейс

## 6.1. Главный экран

При запуске SophyGo пользователь сразу попадает на карту.

Карта должна занимать практически всю доступную область экрана.

Основные элементы:
- Интерактивная карта.
- Маркер текущего местоположения.
- Маркеры достопримечательностей.
- Кнопка определения текущего местоположения.
- Элементы управления масштабом карты.
- Компактная панель Гида.
- Карточка выбранной достопримечательности.

Не перегружать карту кнопками и информацией.

## 6.2. Адаптивность

Интерфейс проектировать Mobile First.

Требования:
- Корректная работа на мобильных экранах.
- Корректная работа на планшетах.
- Удобное использование мышью на компьютере.
- Карточки объектов на мобильных устройствах должны открываться поверх карты.
- Элементы управления должны иметь достаточный размер для нажатия пальцем.
- Не допускать горизонтальной прокрутки.

На компьютере карта также должна занимать основную часть окна браузера.

## 6.3. Визуальный стиль

Общее направление:
- Современный туристический сервис.
- Чистый и понятный интерфейс.
- Акцент на карте и достопримечательностях.
- Минимум лишних элементов.
- Приятные анимации появления карточек и панелей.
- Хорошая читаемость текста.

Не использовать стандартный вид административной панели или корпоративного dashboard.

Не добавлять игровую механику, достижения, уровни и виртуальную валюту.

# 7. Карта

Использовать Leaflet и OpenStreetMap.

Функциональность:
1. Отображать интерактивную карту.
2. Поддерживать масштабирование.
3. Поддерживать перемещение карты.
4. Показывать маркер пользователя.
5. Показывать маркеры достопримечательностей.
6. При выборе маркера открывать карточку объекта.
7. При изменении местоположения пользователя обновлять его маркер.
8. При необходимости центрировать карту на пользователе.

Для первого этапа использовать стандартные OSM-тайлы с обязательной атрибуцией OpenStreetMap.

Не выполнять массовую загрузку тайлов. Для коммерческой эксплуатации впоследствии выбрать подходящего поставщика картографических тайлов.

# 8. Геолокация

Использовать Browser Geolocation API.

Основной механизм:

`navigator.geolocation.watchPosition()`

Функциональность:
- Запрашивать разрешение на определение местоположения.
- Получать координаты пользователя.
- Отображать текущее положение на карте.
- Обновлять положение маркера.
- Обрабатывать отказ в предоставлении разрешения.
- Обрабатывать отсутствие поддержки геолокации.
- Обрабатывать ошибки определения координат.

Геолокация работает только пока приложение активно.

В MVP не реализовывать фоновое отслеживание перемещений.

Не отправлять запрос на backend при каждом GPS-обновлении. В дальнейшем использовать порог изменения координат и ограничение частоты запросов.

## 8.1. Тестовая геолокация

Обязательно реализовать два режима:

**Реальная геолокация**
- Используются реальные координаты устройства.

**Тестовая геолокация**
- Разработчик может выбрать точку на карте.
- Можно установить координаты вручную.
- Можно перемещать тестовую позицию.
- Приложение обрабатывает тестовую позицию так же, как реальную.

Тестовая геолокация должна быть доступна через компактную панель разработчика.

Панель разработчика не должна отображаться в обычном пользовательском режиме.

Тестовый режим нужен для проверки работы Гида без необходимости физически перемещаться по городу.

# 9. Достопримечательности

На первом этапе использовать локальный набор тестовых объектов.

Каждый объект должен содержать:

```typescript
interface Place {
  id: string;
  name: string;
  description: string;
  latitude: number;
  longitude: number;
  category: string;
  images: string[];
}
```

Добавить несколько реальных достопримечательностей Москвы, например:
- Красная площадь.
- Московский Кремль.
- Собор Василия Блаженного.
- Государственный исторический музей.
- Большой театр.

Это тестовые данные, а не окончательная база достопримечательностей.

Требования:
- Отображать объекты на карте.
- Различать объекты по категориям при необходимости.
- Открывать карточку при нажатии на маркер.
- Показывать название, описание и фотографии.
- Закрывать карточку без перезагрузки приложения.

Не реализовывать полноценный каталог достопримечательностей на первом этапе.

# 10. AI-Гид

AI-Гид — центральная функциональность SophyGo.

Его задача — сопровождать путешествие пользователя, рассказывать о достопримечательностях и отвечать на вопросы.

Однако на первом этапе достаточно подготовить интерфейс и базовую логику взаимодействия.

В дальнейшем Гид должен активироваться по двум событиям:

1. Пользователь приблизился к интересной достопримечательности.
2. Пользователь самостоятельно задал вопрос.

Гид не должен постоянно говорить без причины.

## 10.1. Поведение при приближении

Пример:

Пользователь находится рядом с Кремлём.

Приложение обнаруживает, что пользователь приблизился к объекту на расстояние около 100 метров.

Гид предлагает:

«Мы подошли к Московскому Кремлю. Хочешь узнать его историю?»

Пользователь может:
- Послушать рассказ.
- Посмотреть фотографии.
- Отложить рассказ.
- Игнорировать предложение.

Важные правила:
- Не предлагать рассказ об одном объекте повторно слишком часто.
- Не прерывать текущий рассказ новым предложением.
- Не беспокоить пользователя слишком частыми уведомлениями.
- Не запускать аудио без согласия пользователя.

На первом этапе допускается имитация поведения Гида тестовыми сообщениями.

# 11. Карточка достопримечательности

Карточка должна содержать:
- Название.
- Категорию.
- Краткое описание.
- Фотографии.
- Кнопку «Послушать рассказ».
- Возможность закрыть карточку.

Карточка должна удобно отображаться на мобильном устройстве.

Фотографии на первом этапе можно использовать из проверенных публичных источников или локальные тестовые изображения.

При дальнейшем использовании внешних изображений необходимо учитывать лицензии и требования к атрибуции.

# 12. Подготовка к голосовому взаимодействию

Полноценную голосовую инфраструктуру на первом этапе не реализовывать.

В дальнейшем предполагается:
- STT — преобразование речи пользователя в текст.
- LLM — генерация ответа.
- TTS — озвучивание ответа.

Первая реализация должна использовать push-to-talk:

1. Пользователь нажимает кнопку микрофона.
2. Произносит вопрос.
3. Отправляет запись.
4. Получает ответ Гида.
5. Может прервать воспроизведение.

Не начинать с постоянного голосового канала, WebRTC или сложной streaming-инфраструктуры.

# 13. Поддержка Telegram и MAX

Будущие платформы:
- Обычный браузер.
- Telegram Mini App.
- MAX Mini App.

Один React frontend должен работать во всех трёх вариантах.

Для этого предусмотреть интерфейс платформенного адаптера.

Например:

```typescript
interface PlatformAdapter {
  getPlatform(): 'browser' | 'telegram' | 'max';
  ready(): void;
}
```

На первом этапе реализовать BrowserAdapter.

TelegramAdapter и MaxAdapter подключать на следующих этапах.

Важно:
- Не использовать Telegram SDK напрямую в компонентах карты.
- Не использовать MAX Bridge напрямую в компонентах карты.
- Не завязывать бизнес-логику на конкретную платформу.
- Проверку авторизации платформ реализовать на backend.
- Telegram initData проверять на сервере, не доверять initDataUnsafe.

Поддержку GPS, микрофона и других возможностей необходимо отдельно проверить в WebView Telegram и MAX на реальных устройствах.

- Backend на Go.
- PostgreSQL.
- PostGIS.
- Redis.
- Авторизацию пользователей.
- Профили пользователей.
- Синхронизацию Telegram и MAX.
- AI API.
- STT и TTS.
- Постоянное голосовое взаимодействие.
- Игровые механики.
- Достижения.
- Уровни.
- Виртуальную валюту.
- Историю перемещений.
- Фоновую геолокацию.
- Сложную систему кэширования.
- Микросервисную архитектуру.

Эти функции могут появиться позднее, но сейчас они не должны задерживать получение первого работающего результата.

## Этап 1. Базовое приложение

1. Создать React + TypeScript + Vite проект.

2. Разместить объекты на карте.

1. Создать компактную панель Гида.
2. Реализовать тестовые предложения.
3. Реализовать открытие рассказа.
4. Реализовать закрытие и отложенное предложение.
5. Подготовить интерфейс для будущего голосового взаимодействия.

После завершения браузерной версии:
1. Добавить Go backend.
2. Добавить PostgreSQL и PostGIS.

4. Реализовать API поиска ближайших достопримечательностей.

# 17. Инструкции для AI-разработчика

Ты выступаешь в роли senior frontend developer и технического архитектора проекта SophyGo.

Твоя задача — реализовать проект последовательно, небольшими проверяемыми этапами.

Правила разработки:

1. Внимательно изучи это техническое задание.
2. Не пытайся реализовать весь проект за один проход.
3. Начни с первого этапа.
4. Перед добавлением новой зависимости объясняй, зачем она нужна.
5. Не усложняй архитектуру без необходимости.
6. Пиши понятный TypeScript-код.
7. Не используй `any`, если можно определить корректный тип.
8. Обрабатывай ошибки браузерных API.
9. Учитывай мобильные устройства с самого начала.
10. Не оставляй фиктивные реализации там, где требуется работающая функциональность.
11. Не переходи к следующему этапу, пока текущий не проверен.
12. После каждого этапа сообщай:
    - Что реализовано.
    - Какие файлы созданы или изменены.
    - Как запустить приложение.
    - Как проверить функциональность.
    - Какие ограничения остались.

Если обнаруживается неоднозначность в требованиях, сначала предложи наиболее простой вариант и объясни его. Не меняй согласованную концепцию самостоятельно.

**Первая задача: создать минимальный проект SophyGo на React + TypeScript + Vite, подключить Leaflet и OpenStreetMap и получить работающую полноэкранную карту в браузере.**

Не приступай к backend, AI и Telegram-интеграции до завершения базового браузерного этапа.
